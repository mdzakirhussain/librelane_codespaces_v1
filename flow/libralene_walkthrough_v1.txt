 0.  BEFORE YOU START

Set a run tag once per shell session. Every command below reuses it.

    export TAG=example_run

Run all commands from the design directory (the one containing config.json):

    cd /home/zakir/Desktop/fulladder

Sanity-check your installation and see the flow:

    python3 -m librelane --version

================================================================================
 1.  OPTION A - RUN THE WHOLE FLOW IN ONE COMMAND
================================================================================

Purpose: run all 80 steps of the Classic flow end to end. This is what you
should normally do. Use Option B only when you are debugging one stage.

    python3 -m librelane --dockerized ./config.json --run-tag "$TAG"

Re-running the same tag after a failure:

    python3 -m librelane --dockerized ./config.json --run-tag "$TAG" --overwrite

Resume an interrupted run from where it stopped:

    python3 -m librelane --dockerized ./config.json --last-run --from OpenROAD.CTS

Results land in:   ./runs/$TAG/
Final GDSII in:    ./runs/$TAG/final/gds/full_adder.gds


================================================================================
 2.  OPTION B - RUN STAGE BY STAGE
================================================================================

Run these IN THIS EXACT ORDER. See section 6 for why order is not optional.

Note on syntax: "--only X" is the built-in shorthand for "--from X --to X".
Both forms are shown for the first step; afterwards only --only is used.


--------------------------------------------------------------------------------
 2.1  LINT  (steps 1-4)
--------------------------------------------------------------------------------
Purpose: Verilator lints the RTL and the checkers fail the flow on syntax
errors, latch inference, and timing constructs in synthesisable code. Cheap,
and catches problems before you burn an hour on placement.

    python3 -m librelane --dockerized ./config.json --run-tag "$TAG" --to Checker.LintWarnings


--------------------------------------------------------------------------------
 2.2  SYNTHESIS  (steps 5-12)
--------------------------------------------------------------------------------
Purpose: Yosys maps the RTL onto standard cells from the PDK, producing a
gate-level netlist. The trailing checkers catch unmapped cells and stray
assign statements; STAPrePNR gives a first timing estimate with ideal wires.

    python3 -m librelane --dockerized ./config.json --run-tag "$TAG" --to OpenROAD.STAPrePNR

Long form of a single step, for reference:

    python3 -m librelane --dockerized ./config.json --run-tag "$TAG" --from Yosys.Synthesis --to Yosys.Synthesis

Equivalent short form:

    python3 -m librelane --dockerized ./config.json --run-tag "$TAG" --only Yosys.Synthesis

Check afterwards: runs/$TAG/06-yosys-synthesis/reports/stat.rpt


--------------------------------------------------------------------------------
 2.3  FLOORPLAN  (steps 13-19)
--------------------------------------------------------------------------------
Purpose: define the die and core area, lay down the standard-cell row/site
grid, hook up power nets, cut rows around macros, and insert tap and endcap
cells (tap cells prevent latch-up; endcaps terminate the rows).

    python3 -m librelane --dockerized ./config.json --last-run --from OpenROAD.Floorplan --to OpenROAD.TapEndcapInsertion

Individually, if you need to iterate on just one:

    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.Floorplan
    python3 -m librelane --dockerized ./config.json --last-run --only Odb.SetPowerConnections
    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.CutRows
    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.TapEndcapInsertion

Note: Odb.SetPowerConnections is required. Skipping it leaves cells without
VPWR/VGND connections and LVS will fail much later with a confusing error.


--------------------------------------------------------------------------------
 2.4  POWER DISTRIBUTION NETWORK  (steps 20-23)
--------------------------------------------------------------------------------
Purpose: build the power grid - straps, rails, and vias on the upper metals.
This happens BEFORE I/O placement and BEFORE global placement, because the
grid occupies routing resources that placement must be aware of.

    python3 -m librelane --dockerized ./config.json --last-run --from Odb.AddPDNObstructions --to Odb.AddRoutingObstructions

Just the PDN generator:

    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.GeneratePDN

Check afterwards: view the design in OpenROAD (section 4) and confirm the
straps are present and connected.


--------------------------------------------------------------------------------
 2.5  I/O PIN PLACEMENT  (steps 24-27)
--------------------------------------------------------------------------------
Purpose: decide where the top-level ports sit on the die edge.
GlobalPlacementSkipIO does a throwaway placement first so the I/O placer can
put pins near the logic that uses them.

Full group:

    python3 -m librelane --dockerized ./config.json --last-run --from OpenROAD.GlobalPlacementSkipIO --to Odb.ApplyDEFTemplate

DEFAULT (automatic) pin placement:

    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.IOPlacement

CUSTOM pin placement, driven by IO_PIN_ORDER_CFG in config.json:

    python3 -m librelane --dockerized ./config.json --last-run --only Odb.CustomIOPlacement

Your config.json sets "IO_PIN_ORDER_CFG": "dir::pin_order.cfg", so
Odb.CustomIOPlacement is the one that matters for this design. It runs after
OpenROAD.IOPlacement and overrides it. Current pin_order.cfg places:
    #E  Sum, Cout        (east edge)
    #W  A, B, Cin        (west edge)


--------------------------------------------------------------------------------
 2.6  GLOBAL PLACEMENT + POST-GPL REPAIR  (steps 28-33)
--------------------------------------------------------------------------------
Purpose: spread cells across the core to minimise wirelength, then check the
power grid, take a timing snapshot, and let the resizer fix cells with
illegal fanout or slew before legalisation.

    python3 -m librelane --dockerized ./config.json --last-run --from OpenROAD.GlobalPlacement --to Odb.ManualGlobalPlacement

Just the placer:

    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.GlobalPlacement

Do NOT skip OpenROAD.RepairDesignPostGPL. It is what fixes max-slew and
max-fanout violations while there is still room to add buffers.


--------------------------------------------------------------------------------
 2.7  DETAILED PLACEMENT  (step 34)
--------------------------------------------------------------------------------
Purpose: legalisation. Snap every cell onto a legal site on a legal row with
no overlaps. Global placement produces approximate positions; this makes them
manufacturable.

    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.DetailedPlacement


--------------------------------------------------------------------------------
 2.8  CLOCK TREE SYNTHESIS + POST-CTS TIMING  (steps 35-38)
--------------------------------------------------------------------------------
Purpose: build a balanced buffer tree from the clock port to every flop, then
re-run the resizer now that clock skew is real rather than ideal.

    python3 -m librelane --dockerized ./config.json --last-run --from OpenROAD.CTS --to OpenROAD.STAMidPNR-2

Just CTS:

    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.CTS

DESIGN-SPECIFIC NOTE: your config.json sets "CLOCK_PORT": null. full_adder is
purely combinational, so there is no clock tree to build and CTS is
effectively a no-op. The step still runs and still must not be skipped - the
steps after it read the state it writes.


--------------------------------------------------------------------------------
 2.9  GLOBAL ROUTING + ANTENNA REPAIR  (steps 39-46)
--------------------------------------------------------------------------------
Purpose: assign each net to a coarse routing corridor, check for antenna
violations (long metal acting as a charge collector during fabrication and
damaging gate oxide), insert diodes to fix them, and do the final timing
repair now that wire parasitics are estimated.

    python3 -m librelane --dockerized ./config.json --last-run --from OpenROAD.GlobalRouting --to OpenROAD.STAMidPNR-3

Individually:

    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.GlobalRouting
    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.CheckAntennas
    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.RepairAntennas
    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.ResizerTimingPostGRT

This is the last chance to fix timing. After detailed routing the design is
essentially frozen.


--------------------------------------------------------------------------------
 2.10 DETAILED ROUTING  (steps 47-54)
--------------------------------------------------------------------------------
Purpose: commit every net to actual metal shapes and vias on real tracks.
This is by far the longest step. The checkers that follow catch routing DRC
violations, disconnected pins, and pathological wirelength.

    python3 -m librelane --dockerized ./config.json --last-run --from OpenROAD.DetailedRouting --to Checker.WireLength

Just the router:

    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.DetailedRouting

Checker.TrDRC (step 50) belongs HERE, right after routing - it reports the
router's own DRC violations. It is not part of the signoff DRC in section 3.2.

    python3 -m librelane --dockerized ./config.json --last-run --only Checker.TrDRC


--------------------------------------------------------------------------------
 2.11 FILL INSERTION  (steps 55-56)
--------------------------------------------------------------------------------
Purpose: fill leftover gaps in the rows with filler and decap cells, so the
implant and well layers are continuous and the power rails stay quiet.

    python3 -m librelane --dockerized ./config.json --last-run --from OpenROAD.FillInsertion --to Odb.CellFrequencyTables


--------------------------------------------------------------------------------
 2.12 PARASITIC EXTRACTION + POST-PnR STA  (steps 57-59)
--------------------------------------------------------------------------------
Purpose: OpenRCX extracts real R and C from the routed geometry into SPEF
files, then STA re-times the design against them. These are your real,
signoff-grade timing numbers. IRDropReport estimates supply droop.

    python3 -m librelane --dockerized ./config.json --last-run --from OpenROAD.RCX --to OpenROAD.IRDropReport

Individually:

    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.RCX
    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.STAPostPNR

Check afterwards: runs/$TAG/58-openroad-stapostpnr/reports/


--------------------------------------------------------------------------------
 2.13 STREAM-OUT   <<< THIS PRODUCES THE GDSII >>>  (steps 60-64)
--------------------------------------------------------------------------------
Purpose: convert the routed database into GDSII. LibreLane streams out TWICE,
with two independent tools, specifically so they can be compared in section
3.1. Magic runs first, then KLayout.

    python3 -m librelane --dockerized ./config.json --last-run --from Magic.StreamOut --to Odb.CheckDesignAntennaProperties

Individually, in the correct order:

    python3 -m librelane --dockerized ./config.json --last-run --only Magic.StreamOut
    python3 -m librelane --dockerized ./config.json --last-run --only KLayout.StreamOut
    python3 -m librelane --dockerized ./config.json --last-run --only KLayout.Render
    python3 -m librelane --dockerized ./config.json --last-run --only Magic.WriteLEF

Output:
    runs/$TAG/60-magic-streamout/full_adder.gds
    runs/$TAG/61-klayout-streamout/full_adder.gds
    runs/$TAG/final/gds/full_adder.gds        <- the deliverable


================================================================================
 3.  SIGNOFF / VERIFICATION
================================================================================

Everything below runs on the GDSII. None of it changes the layout; it only
tells you whether the layout is correct and manufacturable.


--------------------------------------------------------------------------------
 3.1  XOR - LAYOUT COMPARISON  (steps 65-66)
--------------------------------------------------------------------------------
Purpose: geometrically XOR the Magic GDS against the KLayout GDS. Any shape
that appears in one but not the other is a red flag - it means the two tools
disagree about your layout. A clean run produces an empty XOR.

    python3 -m librelane --dockerized ./config.json --last-run --from KLayout.XOR --to Checker.XOR

Individually:

    python3 -m librelane --dockerized ./config.json --last-run --only KLayout.XOR
    python3 -m librelane --dockerized ./config.json --last-run --only Checker.XOR

Checker.XOR needs KLayout.XOR to have run first - it only reads the result and
decides whether to fail the flow.


--------------------------------------------------------------------------------
 3.2  DRC - DESIGN RULE CHECK  (steps 67-70)
--------------------------------------------------------------------------------
Purpose: verify the layout obeys the foundry's geometric rules (spacing,
width, enclosure, density). Run with both Magic and KLayout; each catches
things the other misses. The two checkers then gate the flow.

    python3 -m librelane --dockerized ./config.json --last-run --from Magic.DRC --to Checker.KLayoutDRC

Individually:

    python3 -m librelane --dockerized ./config.json --last-run --only Magic.DRC
    python3 -m librelane --dockerized ./config.json --last-run --only KLayout.DRC
    python3 -m librelane --dockerized ./config.json --last-run --only Checker.MagicDRC
    python3 -m librelane --dockerized ./config.json --last-run --only Checker.KLayoutDRC

Note there are TWO DRC checkers, Checker.MagicDRC (69) and
Checker.KLayoutDRC (70). Running only one leaves half the DRC results ungated.


--------------------------------------------------------------------------------
 3.3  LVS - LAYOUT VS SCHEMATIC  (steps 71-74)
--------------------------------------------------------------------------------
Purpose: Magic extracts a SPICE netlist from the actual layout geometry, and
Netgen compares it against the synthesised netlist. This proves the thing you
are about to fabricate is electrically the circuit you designed.

    python3 -m librelane --dockerized ./config.json --last-run --from Magic.SpiceExtraction --to Checker.LVS

Individually, in order:

    python3 -m librelane --dockerized ./config.json --last-run --only Magic.SpiceExtraction
    python3 -m librelane --dockerized ./config.json --last-run --only Checker.IllegalOverlap
    python3 -m librelane --dockerized ./config.json --last-run --only Netgen.LVS
    python3 -m librelane --dockerized ./config.json --last-run --only Checker.LVS

Checker.IllegalOverlap (72) belongs to this group - it uses the extraction
result to find cells illegally overlapping. It is not an antenna check.

Netgen.LVS cannot run before Magic.SpiceExtraction; it consumes the SPICE
netlist that step produces.


--------------------------------------------------------------------------------
 3.4  FINAL CHECKERS  (steps 75-80)
--------------------------------------------------------------------------------
Purpose: formal equivalence between RTL and final netlist, then the timing
checkers that fail the flow on setup, hold, slew, and capacitance violations,
then a manufacturability summary.

    python3 -m librelane --dockerized ./config.json --last-run --from Yosys.EQY --to Misc.ReportManufacturability

Individually:

    python3 -m librelane --dockerized ./config.json --last-run --only Yosys.EQY
    python3 -m librelane --dockerized ./config.json --last-run --only Checker.SetupViolations
    python3 -m librelane --dockerized ./config.json --last-run --only Checker.HoldViolations
    python3 -m librelane --dockerized ./config.json --last-run --only Checker.MaxSlewViolations
    python3 -m librelane --dockerized ./config.json --last-run --only Checker.MaxCapViolations
    python3 -m librelane --dockerized ./config.json --last-run --only Misc.ReportManufacturability

Final summary report:
    runs/$TAG/final/metrics.csv
    runs/$TAG/80-misc-reportmanufacturability/


================================================================================
 4.  OPENING RESULTS IN A GUI
================================================================================

These use --flow, not --from/--to. They are separate one-step flows that load
the latest state and open a viewer. They do not modify anything.

OpenROAD - best for placement, routing, PDN, and timing debug:

    python3 -m librelane --dockerized ./config.json --last-run --flow OpenInOpenROAD

KLayout - best for inspecting the final GDSII:

    python3 -m librelane --dockerized ./config.json --last-run --flow OpenInKLayout

Magic - best for extraction and DRC debug:

    python3 -m librelane --dockerized ./config.json --last-run --flow OpenInMagic

You can open the state at any point mid-flow, not just at the end. To inspect
a specific earlier step rather than the latest state, point at its state file:

    python3 -m librelane --dockerized ./config.json --last-run --flow OpenInOpenROAD \
        -i ./runs/$TAG/13-openroad-floorplan/state_out.json

If --dockerized GUI windows do not appear, allow local X connections first:

    xhost +local:docker

================================================================================
 6.  GOTCHAS AND RULES YOU MUST NOT BREAK
================================================================================

(1) ORDER IS NOT OPTIONAL, AND RUNNING OUT OF ORDER DOES NOT ERROR.

    With --last-run, LibreLane loads the most recently MODIFIED state_out.json
    in the run directory - not the state that logically precedes your --from
    step. (See librelane/flows/flow.py, get_latest_file.)

    Consequence: if you run I/O placement before PDN, LibreLane will not
    complain. It will happily feed the wrong state forward and you will get a
    broken or silently degraded design. Always follow section 5's numbering.

(2) --run-tag AND --last-run ARE MUTUALLY EXCLUSIVE.

    Never pass both in one command. Use --run-tag "$TAG" to create or target a
    named run; use --last-run to continue the most recent one. A consistent
    alternative is to use --run-tag "$TAG" on every command, which is
    unambiguous even if you have other runs in flight.

(3) --dockerized MUST COME FIRST.

    Correct:    python3 -m librelane --dockerized ./config.json --only Yosys.Synthesis
    Wrong:      python3 -m librelane ./config.json --dockerized --only Yosys.Synthesis

(4) DO NOT SKIP THE REPAIR AND RESIZER STEPS.

    RepairDesignPostGPL (32), ResizerTimingPostCTS (37), RepairDesignPostGRT
    (41), RepairAntennas (44), ResizerTimingPostGRT (45).

    A step list that jumps straight from GlobalPlacement to DetailedPlacement
    to CTS to routing will complete and will produce a GDSII. That GDSII will
    have unfixed slew, fanout, and antenna violations. It is the single most
    common way to get a "working" flow that fails signoff.

(5) STEPS THAT APPEAR MORE THAN ONCE GET A NUMERIC SUFFIX.

    OpenROAD.STAMidPNR, -1, -2, -3 are four separate invocations at steps 31,
    36, 38, 46. OpenROAD.CheckAntennas and -1 are steps 40 and 49. You must
    use the exact suffixed ID to target a specific one.

(6) CHECKERS ARE NOT ANALYSES.

    Checker.* steps do not compute anything. They read the report produced by
    an earlier step and decide whether to abort the flow. Checker.XOR without
    KLayout.XOR, or Checker.LVS without Netgen.LVS, has nothing to read.

(7) --from A --to B RUNS EVERY STEP FROM A THROUGH B.

    "--from Magic.DRC --to Checker.KLayoutDRC" runs steps 67, 68, 69 and 70,
    not just the two named. This is usually what you want for a whole group -
    just be aware it is a range, not a pair.

(8) --only X IS THE SHORTHAND FOR --from X --to X.

    It overrides both. Prefer it for single steps; it is harder to typo.

(9) OTHER USEFUL FLAGS.

    --overwrite        overwrite an existing run tag instead of failing
    --skip STEP        skip a step within a range
    -j N               parallel jobs (default 2)
    --condensed        terse output, good for logs
    --log-level ERROR  quieten subprocess noise
    -c KEY=VALUE       override one config variable for this run only
    --reproducible ID  package a single step for bug reporting, then abort
    -i FILE            start from a specific state_out.json

(10) NOTES SPECIFIC TO THIS DESIGN (full_adder).

     - CLOCK_PORT is null. The design is combinational, so CTS is a no-op and
       setup/hold checks have nothing to constrain. Do not read a clean timing
       report as evidence that a clocked design would pass.
     - IO_PIN_ORDER_CFG is set, so Odb.CustomIOPlacement (26) is authoritative
       for pin locations, overriding OpenROAD.IOPlacement (25).
     - FP_CORE_UTIL is 5, which is very low. That is fine for a tiny design
       like this - it guarantees routability - but is not representative.


================================================================================
 7.  TROUBLESHOOTING
================================================================================

Flow fails at a checker
    The checker names the report it read. Open the corresponding step
    directory under runs/$TAG/ and read reports/ there. Fix the cause, then
    re-run from the step that produced the report, not from the checker.

"Run directory already exists"
    Add --overwrite, or pick a new tag.

Wrong design state after re-running an early step
    Once you re-run step 20, the states written by steps 21-80 are stale but
    still on disk. --last-run picks by modification time, so this usually
    resolves correctly - but the safe move after re-running an early step is
    to continue forward with an explicit range rather than jumping ahead.

Detailed routing takes forever or fails to converge
    Almost always a placement density or PDN problem, not a router problem.
    Lower PL_TARGET_DENSITY or FP_CORE_UTIL and re-run from floorplan.

GUI does not open under --dockerized
    xhost +local:docker

Inspect any step's inputs and outputs
    runs/$TAG/<NN>-<step-name>/
        config.json      the exact configuration that step saw
        state_out.json   the design state it produced
        reports/         its reports
        *.log            tool output

See what a step accepts
    python3 -m librelane.steps --help
