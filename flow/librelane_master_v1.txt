================================================================================
 1.  INVOCATION FORMS (NATIVE vs DOCKERIZED)
================================================================================

There are three equivalent entry points. Pick one and stay consistent.

  (a) Native, installed console script:

      librelane ./config.json

  (b) Native, via the Python module (identical behaviour, works even if the
      console script is not on PATH):

      python3 -m librelane ./config.json

  (c) Containerized - LibreLane pulls/uses a Docker image and re-invokes
      itself inside it:

      python3 -m librelane --dockerized ./config.json

`--containerized` is an accepted alias for `--dockerized`. Neither is
deprecated; they are the same option.

ARGUMENT ORDER RULE (enforced by the code, not just convention):

    --dockerized must precede ALL other options and the config file.
    The ONLY options allowed before it are:
        -m / --docker-mount   / --container-mount
             --docker-tty     / --container-tty
             --docker-no-tty  / --container-no-tty

    CORRECT:
        python3 -m librelane --dockerized ./config.json --only Yosys.Synthesis
        python3 -m librelane --docker-mount /data --dockerized ./config.json

    WRONG (everything after ./config.json is silently handed to the container
    but --dockerized itself is not seen where you expect it):
        python3 -m librelane ./config.json --dockerized --only Yosys.Synthesis

Mounting an extra directory into the container:

    python3 -m librelane --docker-mount /path/to/dir --dockerized ./config.json

A valid directory is mounted at the same path inside the container. Anything
that is not a valid directory is passed to the container engine verbatim.

X11 / GUI under --dockerized: LibreLane forwards $DISPLAY, mounts
/tmp/.X11-unix and ~/.Xauthority, and runs with `--network host`
automatically. If windows still do not appear, allow local connections:

    xhost +local:docker

If $DISPLAY is unset you get a warning and GUI steps will not work.

TILDE WARNING: LibreLane rejects paths beginning with `~` that the shell has
not expanded. `--pdk-root ~/.ciel` is fine (bash expands it);
`--pdk-root=~/.ciel` and `--pdk-root "~/.ciel"` are both rejected with an
error. Use an absolute path if in doubt.


================================================================================
 2.  CHOOSING A FLOW
================================================================================

Built-in flows in v3.0.6 (the -f/--flow choice list is case-insensitive, so
`--flow Classic` and `--flow classic` are both accepted):

    Classic               80 steps. RTL(Verilog) -> GDSII + full signoff.
                          THIS IS THE DEFAULT. Everything in sections 3-5
                          assumes it.
    Chip                  83 steps. Classic + pad ring, seal ring, filler,
                          density and KLayout antenna checks. For full chips.
    VHDLClassic           72 steps. Classic but entered via Yosys.VHDLSynthesis
                          instead of Verilator lint + Yosys.Synthesis.
    Optimizing            6 steps.  Synthesis -> global placement only.
    SynthesisExploration  3 steps.  Synthesis + pre-PnR STA only.
    OpenInKLayout         1 step.   KLayout.OpenGUI
    OpenInOpenROAD        1 step.   OpenROAD.OpenGUI
    OpenInMagic           1 step.   Magic.OpenGUI

Selecting a flow explicitly:

    python3 -m librelane --dockerized ./config.json --flow Classic --run-tag "$TAG"
    python3 -m librelane --dockerized ./config.json --flow Chip    --run-tag "$TAG"

If you omit --flow, the flow named in config.json's `meta.flow` is used, and
Classic is the fallback.


================================================================================
 3.  OPTION A - RUN THE WHOLE FLOW IN ONE COMMAND
================================================================================

This is what you should normally do. Use section 4 only when debugging.

Fresh run with a named tag:

    python3 -m librelane --dockerized ./config.json --run-tag "$TAG"

Run with an auto-generated tag (RUN_YYYY-MM-DD_HH-MM-SS):

    python3 -m librelane --dockerized ./config.json

Re-run the same tag from scratch, wiping the previous contents:

    python3 -m librelane --dockerized ./config.json --run-tag "$TAG" --overwrite

Resume the most recent run from where it stopped:

    python3 -m librelane --dockerized ./config.json --last-run --from OpenROAD.CTS

Run the whole flow but skip specific steps:

    python3 -m librelane --dockerized ./config.json --run-tag "$TAG" --skip Yosys.EQY

Also copy the final views out to a directory of your choosing:

    python3 -m librelane --dockerized ./config.json --run-tag "$TAG" --save-views-to ./out


================================================================================
 4.  OPTION B - RUN STAGE BY STAGE  (Classic flow)
================================================================================

Run these IN THIS EXACT ORDER. Section 11 explains why the order is not
optional and why running out of order does not raise an error.

SYNTAX NOTE
    --only X   is the built-in shorthand for  --from X --to X
               It is a real flag in v3.0.6, and it OVERRIDES both --from and
               --to if all three are given. Prefer it for single steps.
    --from A --to B  runs EVERY step from A through B inclusive, not just the
               two named ones.

TAG NOTE
    The first command creates the run, so it uses --run-tag "$TAG".
    Every command after it continues that run, so it uses --last-run.
    --run-tag and --last-run are MUTUALLY EXCLUSIVE - never pass both.
    Alternative that is equally valid: use --run-tag "$TAG" on every single
    command. That is unambiguous even if other runs exist. Just do not mix.


--------------------------------------------------------------------------------
 4.1  LINT  (steps 1-4)
--------------------------------------------------------------------------------
Verilator lints the RTL; the checkers fail the flow on syntax errors, latch
inference and non-synthesisable timing constructs. Cheap, and catches problems
before you burn an hour on placement.

    python3 -m librelane --dockerized ./config.json --run-tag "$TAG" --to Checker.LintWarnings

Single steps:

    python3 -m librelane --dockerized ./config.json --last-run --only Verilator.Lint
    python3 -m librelane --dockerized ./config.json --last-run --only Checker.LintErrors


--------------------------------------------------------------------------------
 4.2  SYNTHESIS  (steps 5-12)
--------------------------------------------------------------------------------
Yosys maps RTL onto PDK standard cells. Trailing checkers catch unmapped cells
and stray assign statements; STAPrePNR gives a first timing estimate with
ideal wires.

Whole group:

    python3 -m librelane --dockerized ./config.json --run-tag "$TAG" --to OpenROAD.STAPrePNR

Synthesis alone - long form:

    python3 -m librelane --dockerized ./config.json --run-tag "$TAG" --from Yosys.Synthesis --to Yosys.Synthesis

Synthesis alone - short form (identical):

    python3 -m librelane --dockerized ./config.json --run-tag "$TAG" --only Yosys.Synthesis

Check afterwards: runs/$TAG/06-yosys-synthesis/reports/stat.rpt


--------------------------------------------------------------------------------
 4.3  FLOORPLAN + TAP/ENDCAP  (steps 13-19)
--------------------------------------------------------------------------------
Define die and core area, lay down the standard-cell row/site grid, hook up
power nets, cut rows around macros, insert tap cells (prevent latch-up) and
endcap cells (terminate the rows).

Whole group:

    python3 -m librelane --dockerized ./config.json --last-run --from OpenROAD.Floorplan --to OpenROAD.TapEndcapInsertion

Individually:

    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.Floorplan
    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.DumpRCValues
    python3 -m librelane --dockerized ./config.json --last-run --only Odb.CheckMacroAntennaProperties
    python3 -m librelane --dockerized ./config.json --last-run --only Odb.SetPowerConnections
    python3 -m librelane --dockerized ./config.json --last-run --only Odb.ManualMacroPlacement
    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.CutRows
    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.TapEndcapInsertion

Do not skip Odb.SetPowerConnections. Without it, cells have no VPWR/VGND
connections and LVS fails much later with a confusing error.


--------------------------------------------------------------------------------
 4.4  POWER DISTRIBUTION NETWORK  (steps 20-23)
--------------------------------------------------------------------------------
Build the power grid - straps, rails, vias on the upper metals. This happens
BEFORE I/O placement and BEFORE global placement, because the grid occupies
routing resources that placement must be aware of.

Whole group:

    python3 -m librelane --dockerized ./config.json --last-run --from Odb.AddPDNObstructions --to Odb.AddRoutingObstructions

Individually:

    python3 -m librelane --dockerized ./config.json --last-run --only Odb.AddPDNObstructions
    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.GeneratePDN
    python3 -m librelane --dockerized ./config.json --last-run --only Odb.RemovePDNObstructions
    python3 -m librelane --dockerized ./config.json --last-run --only Odb.AddRoutingObstructions


--------------------------------------------------------------------------------
 4.5  I/O PIN PLACEMENT  (steps 24-27)
--------------------------------------------------------------------------------
Decide where top-level ports sit on the die edge. GlobalPlacementSkipIO does a
throwaway placement first so the I/O placer can put pins near the logic that
uses them.

Whole group (runs whichever placer applies - see section 7):

    python3 -m librelane --dockerized ./config.json --last-run --from OpenROAD.GlobalPlacementSkipIO --to Odb.ApplyDEFTemplate

# When DEFAULT (automatic) IO placement, use the below

    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.IOPlacement

# When CUSTOM IO placement (driven by IO_PIN_ORDER_CFG), use the below

    python3 -m librelane --dockerized ./config.json --last-run --only Odb.CustomIOPlacement

# When IO placement comes from a DEF template (FP_DEF_TEMPLATE), use the below

    python3 -m librelane --dockerized ./config.json --last-run --only Odb.ApplyDEFTemplate

Read section 7 before using these - the two placers self-select based on your
config, and running "the wrong one" is a silent no-op, not an error.


--------------------------------------------------------------------------------
 4.6  GLOBAL PLACEMENT + POST-GPL REPAIR  (steps 28-33)
--------------------------------------------------------------------------------
Spread cells across the core to minimise wirelength, check the power grid,
take a timing snapshot, then let the resizer fix cells with illegal fanout or
slew before legalisation.

Whole group:

    python3 -m librelane --dockerized ./config.json --last-run --from OpenROAD.GlobalPlacement --to Odb.ManualGlobalPlacement

Individually:

    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.GlobalPlacement
    python3 -m librelane --dockerized ./config.json --last-run --only Odb.WriteVerilogHeader
    python3 -m librelane --dockerized ./config.json --last-run --only Checker.PowerGridViolations
    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.STAMidPNR
    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.RepairDesignPostGPL
    python3 -m librelane --dockerized ./config.json --last-run --only Odb.ManualGlobalPlacement

Do NOT skip OpenROAD.RepairDesignPostGPL. It fixes max-slew and max-fanout
violations while there is still room to add buffers.


--------------------------------------------------------------------------------
 4.7  DETAILED PLACEMENT / LEGALISATION  (step 34)
--------------------------------------------------------------------------------
Snap every cell onto a legal site on a legal row with no overlaps.

    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.DetailedPlacement


--------------------------------------------------------------------------------
 4.8  CLOCK TREE SYNTHESIS + POST-CTS TIMING  (steps 35-38)
--------------------------------------------------------------------------------
Build a balanced buffer tree from the clock port to every flop, then re-run
the resizer now that clock skew is real rather than ideal.

Whole group:

    python3 -m librelane --dockerized ./config.json --last-run --from OpenROAD.CTS --to OpenROAD.STAMidPNR-2

Individually:

    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.CTS
    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.STAMidPNR-1
    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.ResizerTimingPostCTS
    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.STAMidPNR-2


--------------------------------------------------------------------------------
 4.9  GLOBAL ROUTING + ANTENNA REPAIR  (steps 39-46)
--------------------------------------------------------------------------------
Assign each net to a coarse routing corridor, check for antenna violations
(long metal collecting charge during fabrication and damaging gate oxide),
insert diodes to fix them, and do the final timing repair now that wire
parasitics are estimated.

Whole group:

    python3 -m librelane --dockerized ./config.json --last-run --from OpenROAD.GlobalRouting --to OpenROAD.STAMidPNR-3

Individually:

    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.GlobalRouting
    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.CheckAntennas
    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.RepairDesignPostGRT
    python3 -m librelane --dockerized ./config.json --last-run --only Odb.DiodesOnPorts
    python3 -m librelane --dockerized ./config.json --last-run --only Odb.HeuristicDiodeInsertion
    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.RepairAntennas
    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.ResizerTimingPostGRT
    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.STAMidPNR-3

This is the last chance to fix timing. After detailed routing the design is
essentially frozen.


--------------------------------------------------------------------------------
 4.10 DETAILED ROUTING  (steps 47-54)
--------------------------------------------------------------------------------
Commit every net to actual metal shapes and vias on real tracks. By far the
longest step. The checkers that follow catch routing DRC violations,
disconnected pins and pathological wirelength.

Whole group:

    python3 -m librelane --dockerized ./config.json --last-run --from OpenROAD.DetailedRouting --to Checker.WireLength

Individually:

    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.DetailedRouting
    python3 -m librelane --dockerized ./config.json --last-run --only Odb.RemoveRoutingObstructions
    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.CheckAntennas-1
    python3 -m librelane --dockerized ./config.json --last-run --only Checker.TrDRC
    python3 -m librelane --dockerized ./config.json --last-run --only Odb.ReportDisconnectedPins
    python3 -m librelane --dockerized ./config.json --last-run --only Checker.DisconnectedPins
    python3 -m librelane --dockerized ./config.json --last-run --only Odb.ReportWireLength
    python3 -m librelane --dockerized ./config.json --last-run --only Checker.WireLength

Checker.TrDRC (step 50) belongs HERE, right after routing - it reports the
router's own DRC violations. It is NOT part of the signoff DRC in section 5.2.

Note the suffix: the antenna check after detailed routing is
OpenROAD.CheckAntennas-1 (step 49), a different invocation from
OpenROAD.CheckAntennas (step 40).


--------------------------------------------------------------------------------
 4.11 FILL INSERTION  (steps 55-56)
--------------------------------------------------------------------------------
Fill leftover gaps in the rows with filler and decap cells, so implant and
well layers are continuous and the power rails stay quiet.

    python3 -m librelane --dockerized ./config.json --last-run --from OpenROAD.FillInsertion --to Odb.CellFrequencyTables

Individually:

    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.FillInsertion
    python3 -m librelane --dockerized ./config.json --last-run --only Odb.CellFrequencyTables


--------------------------------------------------------------------------------
 4.12 PARASITIC EXTRACTION + POST-PnR STA  (steps 57-59)
--------------------------------------------------------------------------------
OpenRCX extracts real R and C from the routed geometry into SPEF files, then
STA re-times the design against them. These are your real, signoff-grade
timing numbers. IRDropReport estimates supply droop.

    python3 -m librelane --dockerized ./config.json --last-run --from OpenROAD.RCX --to OpenROAD.IRDropReport

Individually:

    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.RCX
    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.STAPostPNR
    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.IRDropReport

Check afterwards: runs/$TAG/58-openroad-stapostpnr/reports/


--------------------------------------------------------------------------------
 4.13 STREAM-OUT   <<< THIS PRODUCES THE GDSII >>>  (steps 60-64)
--------------------------------------------------------------------------------
Convert the routed database into GDSII. The Classic flow streams out TWICE,
with two independent tools, specifically so they can be compared by the XOR
check in section 5.1. Magic runs first, then KLayout.

    python3 -m librelane --dockerized ./config.json --last-run --from Magic.StreamOut --to Odb.CheckDesignAntennaProperties

Individually, in the correct order:

    python3 -m librelane --dockerized ./config.json --last-run --only Magic.StreamOut
    python3 -m librelane --dockerized ./config.json --last-run --only KLayout.StreamOut
    python3 -m librelane --dockerized ./config.json --last-run --only KLayout.Render
    python3 -m librelane --dockerized ./config.json --last-run --only Magic.WriteLEF
    python3 -m librelane --dockerized ./config.json --last-run --only Odb.CheckDesignAntennaProperties

Output (DESIGN_NAME substituted for your top module):

    runs/$TAG/60-magic-streamout/<DESIGN_NAME>.gds
    runs/$TAG/61-klayout-streamout/<DESIGN_NAME>.gds
    runs/$TAG/final/gds/<DESIGN_NAME>.gds          <- the deliverable


================================================================================
 5.  SIGNOFF / VERIFICATION
================================================================================

Everything below runs on the GDSII. None of it changes the layout; it only
tells you whether the layout is correct and manufacturable.


--------------------------------------------------------------------------------
 5.1  XOR - LAYOUT COMPARISON  (steps 65-66)
--------------------------------------------------------------------------------
Geometrically XOR the Magic GDS against the KLayout GDS. Any shape present in
one but not the other means the two tools disagree about your layout. A clean
run produces an empty XOR.

    python3 -m librelane --dockerized ./config.json --last-run --from KLayout.XOR --to Checker.XOR

Individually:

    python3 -m librelane --dockerized ./config.json --last-run --only KLayout.XOR
    python3 -m librelane --dockerized ./config.json --last-run --only Checker.XOR


--------------------------------------------------------------------------------
 5.2  DRC - DESIGN RULE CHECK  (steps 67-70)
--------------------------------------------------------------------------------
Verify the layout obeys the foundry's geometric rules (spacing, width,
enclosure, density). Run with both Magic and KLayout; each catches things the
other misses. Two separate checkers then gate the flow.

    python3 -m librelane --dockerized ./config.json --last-run --from Magic.DRC --to Checker.KLayoutDRC

Individually:

    python3 -m librelane --dockerized ./config.json --last-run --only Magic.DRC
    python3 -m librelane --dockerized ./config.json --last-run --only KLayout.DRC
    python3 -m librelane --dockerized ./config.json --last-run --only Checker.MagicDRC
    python3 -m librelane --dockerized ./config.json --last-run --only Checker.KLayoutDRC

There are TWO DRC checkers - Checker.MagicDRC (69) and Checker.KLayoutDRC
(70). Running only one leaves half the DRC results ungated.


--------------------------------------------------------------------------------
 5.3  LVS - LAYOUT VS SCHEMATIC  (steps 71-74)
--------------------------------------------------------------------------------
Magic extracts a SPICE netlist from the actual layout geometry, and Netgen
compares it against the synthesised netlist. This proves the thing you are
about to fabricate is electrically the circuit you designed.

    python3 -m librelane --dockerized ./config.json --last-run --from Magic.SpiceExtraction --to Checker.LVS

Individually, in order:

    python3 -m librelane --dockerized ./config.json --last-run --only Magic.SpiceExtraction
    python3 -m librelane --dockerized ./config.json --last-run --only Checker.IllegalOverlap
    python3 -m librelane --dockerized ./config.json --last-run --only Netgen.LVS
    python3 -m librelane --dockerized ./config.json --last-run --only Checker.LVS

Checker.IllegalOverlap (72) belongs to this group - it uses the extraction
result to find cells illegally overlapping. It is not an antenna check.

Netgen.LVS cannot run before Magic.SpiceExtraction; it consumes the SPICE
netlist that step produces.


--------------------------------------------------------------------------------
 5.4  FINAL CHECKERS  (steps 75-80)
--------------------------------------------------------------------------------
Formal equivalence between RTL and final netlist, then the timing checkers
that fail the flow on setup, hold, slew and capacitance violations, then a
manufacturability summary.

    python3 -m librelane --dockerized ./config.json --last-run --from Yosys.EQY --to Misc.ReportManufacturability

Individually:

    python3 -m librelane --dockerized ./config.json --last-run --only Yosys.EQY
    python3 -m librelane --dockerized ./config.json --last-run --only Checker.SetupViolations
    python3 -m librelane --dockerized ./config.json --last-run --only Checker.HoldViolations
    python3 -m librelane --dockerized ./config.json --last-run --only Checker.MaxSlewViolations
    python3 -m librelane --dockerized ./config.json --last-run --only Checker.MaxCapViolations
    python3 -m librelane --dockerized ./config.json --last-run --only Misc.ReportManufacturability

Final summary:
    runs/$TAG/final/metrics.csv
    runs/$TAG/final/metrics.json
    runs/$TAG/80-misc-reportmanufacturability/


================================================================================
 6.  OPENING RESULTS IN A GUI
================================================================================

These use --flow, NOT --from/--to. They are separate one-step flows that load
the latest state and open a viewer. They do not modify the design.

OpenROAD - best for placement, routing, PDN and timing debug:

    python3 -m librelane --dockerized ./config.json --last-run --flow OpenInOpenROAD

KLayout - best for inspecting the final GDSII:

    python3 -m librelane --dockerized ./config.json --last-run --flow OpenInKLayout

Magic - best for extraction and DRC debug:

    python3 -m librelane --dockerized ./config.json --last-run --flow OpenInMagic

Flow names are case-insensitive, so `--flow openinklayout` works identically.

To inspect a SPECIFIC earlier step rather than the latest state, point at that
step's state_out.json with -i / --with-initial-state:

    python3 -m librelane --dockerized ./config.json --last-run --flow OpenInOpenROAD \
        -i ./runs/$TAG/13-openroad-floorplan/state_out.json

If GUI windows do not appear under --dockerized:

    xhost +local:docker


================================================================================
 7.  MANUAL vs DEFAULT: WHERE YOU ACTUALLY HAVE A CHOICE
================================================================================

These are the points in the Classic flow where LibreLane offers a "do it
automatically" step and a "do it the way I said" step. In every case BOTH
steps are present in the flow and each one decides at runtime whether to run
or skip itself, based on your config.json. Running the inapplicable one is a
harmless no-op, not an error - which is exactly why it is easy to be confused
about which one did the work.


--------------------------------------------------------------------------------
 7.1  I/O PIN PLACEMENT   (steps 25 / 26 / 27)
--------------------------------------------------------------------------------
Relevant config variables:  IO_PIN_ORDER_CFG, FP_DEF_TEMPLATE

  Config state                         Step that actually does the work
  -----------------------------------  ----------------------------------------
  IO_PIN_ORDER_CFG = null (default)    OpenROAD.IOPlacement       (step 25)
  IO_PIN_ORDER_CFG = "<path>"          Odb.CustomIOPlacement      (step 26)
  FP_DEF_TEMPLATE  = "<path>"          Odb.ApplyDEFTemplate       (step 27)

Exact self-skip logic in v3.0.6:
  * OpenROAD.IOPlacement skips itself if IO_PIN_ORDER_CFG is not null,
    and also skips itself if FP_DEF_TEMPLATE is not null.
  * Odb.CustomIOPlacement skips itself if IO_PIN_ORDER_CFG is null,
    logging "No custom I/O placement file configured, skipping…".

# When default IO placement use the below

python3 -m librelane --dockerized ./config.json --last-run --from OpenROAD.IOPlacement --to OpenROAD.IOPlacement

# When custom IO placement use the below

python3 -m librelane --dockerized ./config.json --last-run --from Odb.CustomIOPlacement --to Odb.CustomIOPlacement

(Short forms, identical behaviour:)

    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.IOPlacement
    python3 -m librelane --dockerized ./config.json --last-run --only Odb.CustomIOPlacement

To switch from default to custom, you must edit config.json - there is no CLI
flag for it. Either edit the file, or override for one run only:

    python3 -m librelane --dockerized ./config.json --run-tag "$TAG" \
        -c 'IO_PIN_ORDER_CFG="dir::pin_order.cfg"'

Note IO_PIN_ORDER_CFG replaces the OpenLane-era name FP_PIN_ORDER_CFG.
FP_PIN_ORDER_CFG is still accepted as a deprecated alias in config.json, but
it is NOT accepted by `-c`/--override-config, which requires current names.
Use IO_PIN_ORDER_CFG.

Pin order config file syntax (per the official reference):

    #N / #S / #E / #W       start the north / south / east / west section
    <regex>                 a pin name as a regular expression; regex
                            metacharacters must be escaped, e.g. x\[0\]
    @min_distance=<um>      minimum spacing between pins; global or per-section
    @bus_major              sort by bus name then bit number  (default)
    @bit_major              sort by bit number then bus name
    $<n>                    insert n virtual/placeholder pins

    Example:
        #N
        @min_distance=0.1
        x.*

        #S
        $1
        rst

        #E
        clk

        #W
        p
        y

================================================================================
 11.  RULES YOU MUST NOT BREAK
================================================================================

(1) ORDER IS NOT OPTIONAL, AND RUNNING OUT OF ORDER DOES NOT ERROR.

    --last-run picks the run directory with the newest modification time.
    Within that directory, if you do not pass -i, the initial state is the
    NEWEST state_out.json by modification time, found recursively - not the
    state that logically precedes your --from step.
    (librelane/flows/flow.py, librelane/common/misc.py: get_latest_file)

    Consequence: if you run I/O placement before PDN, LibreLane will not
    complain. It will feed the wrong state forward and you get a broken or
    silently degraded design. Follow section 12's numbering.

(2) --run-tag AND --last-run ARE MUTUALLY EXCLUSIVE.

    Passing both raises "tag and last_run cannot be used simultaneously."
    Pick one convention per session and keep to it.

(3) --dockerized MUST COME FIRST.  See section 1 for the exact rule.

(4) DO NOT SKIP THE REPAIR AND RESIZER STEPS.

    RepairDesignPostGPL (32), ResizerTimingPostCTS (37),
    RepairDesignPostGRT (41), RepairAntennas (44), ResizerTimingPostGRT (45).

    A step list that jumps straight from GlobalPlacement to DetailedPlacement
    to CTS to routing will complete and produce a GDSII. That GDSII will have
    unfixed slew, fanout and antenna violations. It is the most common way to
    get a "working" flow that fails signoff.

(5) STEPS THAT APPEAR MORE THAN ONCE GET A NUMERIC SUFFIX.

    OpenROAD.STAMidPNR, -1, -2, -3 are four separate invocations at steps 31,
    36, 38, 46. OpenROAD.CheckAntennas and CheckAntennas-1 are steps 40 and
    49. You must use the exact suffixed ID to target a specific one.

(6) CHECKERS ARE NOT ANALYSES.

    Checker.* steps compute nothing. They read a report produced by an earlier
    step and decide whether to abort the flow. Checker.XOR without KLayout.XOR,
    or Checker.LVS without Netgen.LVS, has nothing to read.

(7) --from A --to B IS A RANGE, NOT A PAIR.

    "--from Magic.DRC --to Checker.KLayoutDRC" runs steps 67, 68, 69 AND 70.

(8) --only X IS THE SHORTHAND FOR --from X --to X, AND OVERRIDES BOTH.

(9) SELF-SKIPPING STEPS ARE NOT ERRORS.

    Several steps decide at runtime to do nothing (section 7). Read the log
    line - "skipping <id>…" - rather than assuming the step did the work.

(10) DEPRECATED CONFIG NAMES ARE ACCEPTED IN config.json, NOT IN -c.

     Examples of renames in this version:
         FP_PIN_ORDER_CFG          -> IO_PIN_ORDER_CFG
         GRT_OBS                   -> ROUTING_OBSTRUCTIONS
         QUIT_ON_UNMATCHED_IO      -> ERRORS_ON_UNMATCHED_IO
         MACRO_PLACEMENT_CFG       -> MACROS
     Prefer current names everywhere.

================================================================================
 14.  TROUBLESHOOTING
================================================================================

Flow fails at a checker
    The checker names the report it read. Open the corresponding step
    directory under runs/$TAG/ and read reports/ there. Fix the CAUSE, then
    re-run from the step that produced the report, not from the checker.

"Run directory already exists"
    Add --overwrite, or pick a new tag.

"tag and last_run cannot be used simultaneously"
    You passed both --run-tag and --last-run. Drop one.

"last_run used without any existing runs"
    You used --last-run before any run existed. Start with --run-tag.

Path starting with a tilde is rejected
    Let bash expand it: `--pdk-root ~/.ciel`, never `--pdk-root=~/.ciel` and
    never `--pdk-root "~/.ciel"`. Or use an absolute path.

Wrong design state after re-running an early step
    Once you re-run step 20, the states written by steps 21-80 are stale but
    still on disk. Initial-state selection is by modification time, so it
    usually resolves correctly - but the safe move after re-running an early
    step is to continue forward with an explicit range, or pin the state
    explicitly with -i.

Detailed routing takes forever or fails to converge
    Almost always a placement density or PDN problem, not a router problem.
    Lower PL_TARGET_DENSITY or FP_CORE_UTIL and re-run from floorplan.

GUI does not open under --dockerized
    xhost +local:docker
    and confirm $DISPLAY is set in the shell you launch from.

A step "did nothing"
    Check the log for "skipping <id>…". See section 7 - several steps
    self-skip based on config.

Inspect any step's inputs and outputs
    runs/$TAG/<NN>-<step-name>/
        config.json      the exact configuration that step saw
        state_out.json   the design state it produced
        reports/         its reports
        *.log            tool output

See what the step CLI accepts
    python3 -m librelane.steps --help
    python3 -m librelane.steps run --help
