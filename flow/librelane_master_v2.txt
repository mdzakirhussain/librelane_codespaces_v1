================================================================================
 1.  INVOCATION FORMS (NATIVE vs DOCKERIZED)
================================================================================

There are three equivalent entry points. Pick one and stay consistent.

  (a) Native, installed console script:

      librelane ./config.json

  (b) Native, via the Python module (identical behaviour, works even if the
      console script is not on PATH):

      python3 -m librelane ./config.json

  (c) Containerized - LibreLane pulls/uses a Docker image and re-invokes
      itself inside it:

      python3 -m librelane --dockerized ./config.json

`--containerized` is an accepted alias for `--dockerized`. Neither is
deprecated; they are the same option.

ARGUMENT ORDER RULE (enforced by the code, not just convention):

    --dockerized must precede ALL other options and the config file.
    The ONLY options allowed before it are:
        -m / --docker-mount   / --container-mount
             --docker-tty     / --container-tty
             --docker-no-tty  / --container-no-tty

    CORRECT:
        python3 -m librelane --dockerized ./config.json --only Yosys.Synthesis
        python3 -m librelane --docker-mount /data --dockerized ./config.json

    WRONG (everything after ./config.json is silently handed to the container
    but --dockerized itself is not seen where you expect it):
        python3 -m librelane ./config.json --dockerized --only Yosys.Synthesis

TTY NOTE - ONLY APPLIES IF YOUR SHELL HAS NO TERMINAL

    IF YOU ARE TYPING INTO A NORMAL TERMINAL, IGNORE THIS AND USE THE PLAIN
    --dockerized COMMANDS THROUGHOUT THIS DOCUMENT. Nothing extra is needed.

    The default is --docker-tty, i.e. LibreLane passes -t to docker. That is
    correct and works in any interactive shell.

    It only breaks where stdin is NOT a terminal - a pipeline, `bash -c`, a
    cron job, ssh without -t, CI, or an automation/agent harness. There the
    first dockerized command dies immediately with:

        INFO  Running containerized command:
        cannot attach stdin to a TTY-enabled container because stdin is not a terminal

    Nothing runs and no run directory is created. The fix is --docker-no-tty,
    which like --docker-mount MUST come BEFORE --dockerized:

        python3 -m librelane --docker-no-tty --dockerized ./config.json --run-tag "$TAG"

    CONTROLLED TEST (same command, same design, only the TTY differs):

        shell state          flag used          result
        -------------------  -----------------  ---------------------------
        `tty` -> not a tty   (none)             exit 1, TTY error above
        real PTY (`script`)  (none)             exit 0, "Flow complete"

    So the flag is ENVIRONMENT-SPECIFIC, not a general requirement. Add it in
    scripts and CI; leave it out when working by hand. It is harmless if
    present, so scripts intended to run in both places can keep it.

    Placing it after --dockerized has NO EFFECT - it is silently forwarded
    into the container as a flow argument instead of configuring the engine.

Mounting an extra directory into the container:

    python3 -m librelane --docker-mount /path/to/dir --dockerized ./config.json

A valid directory is mounted at the same path inside the container.

CAVEAT (verified against librelane/container.py): the --help text says a
non-directory value "will be passed to the container engine verbatim". That is
misleading. The code does:

        mount_args += ["-v", f"{mount}"]

i.e. the value is ALWAYS consumed as the argument of a -v flag. You can use it
to write a raw bind-mount spec such as /host/path:/container/path:ro, but you
CANNOT use it to inject other engine flags. In particular this does NOT work:

        --docker-mount "-e LIBGL_ALWAYS_SOFTWARE=1"      # becomes -v "-e LIBGL_..."

The only environment variables LibreLane forwards into the container are
DISPLAY (for GUIs), PDK_ROOT, PDK and STD_CELL_LIBRARY. To set anything else
you must invoke the container engine yourself instead of using --dockerized.

X11 / GUI under --dockerized: LibreLane forwards $DISPLAY, mounts
/tmp/.X11-unix and ~/.Xauthority, and runs with `--network host`
automatically. If windows still do not appear, allow local connections:

    xhost +local:docker

If $DISPLAY is unset you get a warning and GUI steps will not work.

TILDE WARNING: LibreLane rejects paths beginning with `~` that the shell has
not expanded. `--pdk-root ~/.ciel` is fine (bash expands it);
`--pdk-root=~/.ciel` and `--pdk-root "~/.ciel"` are both rejected with an
error. Use an absolute path if in doubt.


================================================================================
 2.  CHOOSING A FLOW
================================================================================

Built-in flows in v3.0.6 (the -f/--flow choice list is case-insensitive, so
`--flow Classic` and `--flow classic` are both accepted):

    Classic               80 steps. RTL(Verilog) -> GDSII + full signoff.
                          THIS IS THE DEFAULT. Everything in sections 3-5
                          assumes it.
    Chip                  83 steps. Classic + pad ring, seal ring, filler,
                          density and KLayout antenna checks. For full chips.
    VHDLClassic           72 steps. Classic but entered via Yosys.VHDLSynthesis
                          instead of Verilator lint + Yosys.Synthesis.
    Optimizing            6 steps.  Synthesis -> global placement only.
    SynthesisExploration  3 steps.  Synthesis + pre-PnR STA only.
    OpenInKLayout         1 step.   KLayout.OpenGUI
    OpenInOpenROAD        1 step.   OpenROAD.OpenGUI
    OpenInMagic           1 step.   Magic.OpenGUI

Selecting a flow explicitly:

    python3 -m librelane --dockerized ./config.json --flow Classic --run-tag "$TAG"
    python3 -m librelane --dockerized ./config.json --flow Chip    --run-tag "$TAG"

If you omit --flow, the flow named in config.json's `meta.flow` is used, and
Classic is the fallback.


================================================================================
 3.  OPTION A - RUN THE WHOLE FLOW IN ONE COMMAND
================================================================================

This is what you should normally do. Use section 4 only when debugging.

Fresh run with a named tag:

    python3 -m librelane --dockerized ./config.json --run-tag "$TAG"

Run with an auto-generated tag (RUN_YYYY-MM-DD_HH-MM-SS):

    python3 -m librelane --dockerized ./config.json

Re-run the same tag from scratch, wiping the previous contents:

    python3 -m librelane --dockerized ./config.json --run-tag "$TAG" --overwrite

Resume the most recent run from where it stopped:

    python3 -m librelane --dockerized ./config.json --last-run --from OpenROAD.CTS

Run the whole flow but skip specific steps:

    python3 -m librelane --dockerized ./config.json --run-tag "$TAG" --skip Yosys.EQY

Also copy the final views out to a directory of your choosing:

    python3 -m librelane --dockerized ./config.json --run-tag "$TAG" --save-views-to ./out


================================================================================
 4.  OPTION B - RUN STAGE BY STAGE  (Classic flow)
================================================================================

Run these IN THIS EXACT ORDER. Section 11 explains why the order is not
optional and why running out of order does not raise an error.

SYNTAX NOTE
    --only X   is the built-in shorthand for  --from X --to X
               It is a real flag in v3.0.6, and it OVERRIDES both --from and
               --to if all three are given. Prefer it for single steps.
    --from A --to B  runs EVERY step from A through B inclusive, not just the
               two named ones.

TAG NOTE
    The first command creates the run, so it uses --run-tag "$TAG".
    Every command after it continues that run, so it uses --last-run.
    --run-tag and --last-run are MUTUALLY EXCLUSIVE - never pass both.
    Alternative that is equally valid: use --run-tag "$TAG" on every single
    command. That is unambiguous even if other runs exist. Just do not mix.


--------------------------------------------------------------------------------
 4.1  LINT  (steps 1-4)
--------------------------------------------------------------------------------
Verilator lints the RTL; the checkers fail the flow on syntax errors, latch
inference and non-synthesisable timing constructs. Cheap, and catches problems
before you burn an hour on placement.

    python3 -m librelane --dockerized ./config.json --run-tag "$TAG" --to Checker.LintWarnings

Single steps:

    python3 -m librelane --dockerized ./config.json --last-run --only Verilator.Lint
    python3 -m librelane --dockerized ./config.json --last-run --only Checker.LintErrors


--------------------------------------------------------------------------------
 4.2  SYNTHESIS  (steps 5-12)
--------------------------------------------------------------------------------
Yosys maps RTL onto PDK standard cells. Trailing checkers catch unmapped cells
and stray assign statements; STAPrePNR gives a first timing estimate with
ideal wires.

Whole group - CORRECT FORM (continues the run created in 4.1):

    python3 -m librelane --dockerized ./config.json --last-run --from Yosys.JsonHeader --to OpenROAD.STAPrePNR

  DO NOT USE (this was v1's command, and it is wrong here):

    python3 -m librelane --dockerized ./config.json --run-tag "$TAG" --to OpenROAD.STAPrePNR

  VERIFIED FAILURE MODE: --to without --from starts at step 1, so this
  re-runs Verilator.Lint and the three lint checkers a SECOND time inside the
  same run directory. Observed result - lint appears twice and every later
  ordinal is shifted by 4:

        01-verilator-lint                 <- first invocation
        02-checker-linttimingconstructs
        03-checker-linterrors
        04-checker-lintwarnings
        05-verilator-lint                 <- SAME STEPS AGAIN
        06-checker-linttimingconstructs
        07-checker-linterrors
        08-checker-lintwarnings
        09-yosys-jsonheader
        10-yosys-synthesis                <- expected 06

  It does not error, it just wastes time and makes every directory number in
  section 10 wrong. Once you have created the run in 4.1, every subsequent
  stage must use --last-run --from … --to … .

Synthesis alone - long form:

    python3 -m librelane --dockerized ./config.json --last-run --from Yosys.Synthesis --to Yosys.Synthesis

Synthesis alone - short form (identical):

    python3 -m librelane --dockerized ./config.json --last-run --only Yosys.Synthesis

Check afterwards: runs/$TAG/06-yosys-synthesis/reports/stat.rpt

================================================================================
 4A.  GATING VARIABLES (RUN_*) - STEPS THAT ARE OFF BY DEFAULT
================================================================================

This section did not exist in v1 and explains behaviour you WILL hit.

There are TWO different ways a Classic step can end up doing nothing, and they
behave differently on disk. Confusing them is why step directory numbers stop
matching section 12.

  MECHANISM A - GATING VARIABLE (flow level)
      The flow checks a RUN_* config variable BEFORE constructing the step.
      If it is false you get:
          INFO  Gating variable for step 'X' set to 'False'- the step will be skipped.
          INFO  Skipping step 'X'…
      The step does NOT execute, consumes NO ordinal, and NO directory is
      created for it.
      (librelane/flows/sequential.py - `increment_ordinal = False`)

  MECHANISM B - SELF-SKIP (step level, see section 7)
      The step is constructed and executed, and decides inside its own run()
      to return early, e.g.
          INFO  IO_PIN_ORDER_CFG is set. Skipping 'OpenROAD.IOPlacement'…
      The step DOES consume an ordinal and a directory IS created, containing
      config.json, state_in.json, state_out.json and runtime.txt - but no tool
      log and no layout output.

VERIFIED EXAMPLE of mechanism B, from the mux8x1 run in section 16:

    runs/mux8x1_flow/25-openroad-ioplacement/     <- directory exists
        config.json  runtime.txt  state_in.json  state_out.json   (no .log)
    runs/mux8x1_flow/26-odb-customioplacement/    <- actually did the work
        ... mux8x1.def  mux8x1.odb  odb-customioplacement.log ...


--------------------------------------------------------------------------------
 4A.1  THE COMPLETE GATING TABLE (Classic / VHDLClassic, v3.0.6)
--------------------------------------------------------------------------------
Read straight from `Classic.gating_config_vars`. A step is gated off if ANY of
its listed variables is false.

    Step ID                            Gating variable(s)             Default
    ---------------------------------  -----------------------------  -------
    Verilator.Lint                     RUN_LINTER                     True
    Checker.LintErrors                 RUN_LINTER                     True
    Checker.LintWarnings               RUN_LINTER                     True
    Checker.LintTimingConstructs       RUN_LINTER                     True

--------------------------------------------------------------------------------
 4A.2  THE FOUR STEPS THAT ARE OFF BY DEFAULT
--------------------------------------------------------------------------------
In a stock Classic run these four NEVER execute and produce NO directory:

    OpenROAD.RepairDesignPostGRT     RUN_POST_GRT_DESIGN_REPAIR = False
    Odb.HeuristicDiodeInsertion      RUN_HEURISTIC_DIODE_INSERTION = False
    OpenROAD.ResizerTimingPostGRT    RUN_POST_GRT_RESIZER_TIMING = False
    Yosys.EQY                        RUN_EQY = False

The two post-GRT ones are described by upstream, verbatim, as:

    "This is experimental and may result in hangs and/or extended run times."

That is the reason they ship disabled. v1 of this document told you not to
skip them; that was wrong - you cannot "not skip" a step that is off by
default, and turning them on is an explicit, risk-accepting choice.

To turn any of them on for a single run:

    python3 -m librelane --dockerized ./config.json --run-tag "$TAG" \
        -c 'RUN_POST_GRT_DESIGN_REPAIR=true' \
        -c 'RUN_POST_GRT_RESIZER_TIMING=true' \
        -c 'RUN_EQY=true'

Or set them permanently in config.json.

CONSEQUENCE FOR --from / --to: naming a gated step is NOT an error. The range
still runs; the gated step is simply skipped inside it. Verified:

    --from Yosys.EQY --to Misc.ReportManufacturability

completes normally, but Yosys.EQY itself does not run and writes no
equivalence result. If you actually want the equivalence check, set
RUN_EQY=true first.

Note RUN_HEURISTIC_DIODE_INSERTION is additionally forced by LibreLane's own
config resolution logic (librelane/config/config.py) depending on the diode
insertion strategy in use, so its effective value can differ from the raw
default.


================================================================================
 5.  SIGNOFF / VERIFICATION
================================================================================

Everything below runs on the GDSII. None of it changes the layout; it only
tells you whether the layout is correct and manufacturable.


--------------------------------------------------------------------------------
 5.1  XOR - LAYOUT COMPARISON  (steps 65-66)
--------------------------------------------------------------------------------
Geometrically XOR the Magic GDS against the KLayout GDS. Any shape present in
one but not the other means the two tools disagree about your layout. A clean
run produces an empty XOR.

    python3 -m librelane --dockerized ./config.json --last-run --from KLayout.XOR --to Checker.XOR

Individually:

    python3 -m librelane --dockerized ./config.json --last-run --only KLayout.XOR
    python3 -m librelane --dockerized ./config.json --last-run --only Checker.XOR


--------------------------------------------------------------------------------
 5.2  DRC - DESIGN RULE CHECK  (steps 67-70)
--------------------------------------------------------------------------------
Verify the layout obeys the foundry's geometric rules (spacing, width,
enclosure, density). Run with both Magic and KLayout; each catches things the
other misses. Two separate checkers then gate the flow.

    python3 -m librelane --dockerized ./config.json --last-run --from Magic.DRC --to Checker.KLayoutDRC

Individually:

    python3 -m librelane --dockerized ./config.json --last-run --only Magic.DRC
    python3 -m librelane --dockerized ./config.json --last-run --only KLayout.DRC
    python3 -m librelane --dockerized ./config.json --last-run --only Checker.MagicDRC
    python3 -m librelane --dockerized ./config.json --last-run --only Checker.KLayoutDRC

There are TWO DRC checkers - Checker.MagicDRC (69) and Checker.KLayoutDRC
(70). Running only one leaves half the DRC results ungated.


--------------------------------------------------------------------------------
 5.3  LVS - LAYOUT VS SCHEMATIC  (steps 71-74)
--------------------------------------------------------------------------------
Magic extracts a SPICE netlist from the actual layout geometry, and Netgen
compares it against the synthesised netlist. This proves the thing you are
about to fabricate is electrically the circuit you designed.

    python3 -m librelane --dockerized ./config.json --last-run --from Magic.SpiceExtraction --to Checker.LVS

Individually, in order:

    python3 -m librelane --dockerized ./config.json --last-run --only Magic.SpiceExtraction
    python3 -m librelane --dockerized ./config.json --last-run --only Checker.IllegalOverlap
    python3 -m librelane --dockerized ./config.json --last-run --only Netgen.LVS
    python3 -m librelane --dockerized ./config.json --last-run --only Checker.LVS

Checker.IllegalOverlap (72) belongs to this group - it uses the extraction
result to find cells illegally overlapping. It is not an antenna check.

Netgen.LVS cannot run before Magic.SpiceExtraction; it consumes the SPICE
netlist that step produces.


--------------------------------------------------------------------------------
 5.4  FINAL CHECKERS  (steps 75-80)
--------------------------------------------------------------------------------
Formal equivalence between RTL and final netlist, then the timing checkers
that fail the flow on setup, hold, slew and capacitance violations, then a
manufacturability summary.

    python3 -m librelane --dockerized ./config.json --last-run --from Yosys.EQY --to Misc.ReportManufacturability

Individually:

    python3 -m librelane --dockerized ./config.json --last-run --only Yosys.EQY
    python3 -m librelane --dockerized ./config.json --last-run --only Checker.SetupViolations
    python3 -m librelane --dockerized ./config.json --last-run --only Checker.HoldViolations
    python3 -m librelane --dockerized ./config.json --last-run --only Checker.MaxSlewViolations
    python3 -m librelane --dockerized ./config.json --last-run --only Checker.MaxCapViolations
    python3 -m librelane --dockerized ./config.json --last-run --only Misc.ReportManufacturability

Final summary:
    runs/$TAG/final/metrics.csv
    runs/$TAG/final/metrics.json
    runs/$TAG/80-misc-reportmanufacturability/


================================================================================
 6.  OPENING RESULTS IN A GUI
================================================================================

These use --flow, NOT --from/--to. They are separate one-step flows that load
the latest state and open a viewer. They do not modify the design.

OpenROAD - best for placement, routing, PDN and timing debug:

    python3 -m librelane --dockerized ./config.json --last-run --flow OpenInOpenROAD

KLayout - best for inspecting the final GDSII:

    python3 -m librelane --dockerized ./config.json --last-run --flow OpenInKLayout

Magic - best for extraction and DRC debug:

    python3 -m librelane --dockerized ./config.json --last-run --flow OpenInMagic

Flow names are case-insensitive, so `--flow openinklayout` works identically.

To inspect a SPECIFIC earlier step rather than the latest state, point at that
step's state_out.json with -i / --with-initial-state:

    python3 -m librelane --dockerized ./config.json --last-run --flow OpenInOpenROAD \
        -i ./runs/$TAG/13-openroad-floorplan/state_out.json

If GUI windows do not appear under --dockerized:

    xhost +local:docker


================================================================================
 7.  MANUAL vs DEFAULT: WHERE YOU ACTUALLY HAVE A CHOICE
================================================================================

These are the points in the Classic flow where LibreLane offers a "do it
automatically" step and a "do it the way I said" step. In every case BOTH
steps are present in the flow and each one decides at runtime whether to run
or skip itself, based on your config.json. Running the inapplicable one is a
harmless no-op, not an error - which is exactly why it is easy to be confused
about which one did the work.


--------------------------------------------------------------------------------
 7.1  I/O PIN PLACEMENT   (steps 25 / 26 / 27)
--------------------------------------------------------------------------------
Relevant config variables:  IO_PIN_ORDER_CFG, FP_DEF_TEMPLATE

  Config state                         Step that actually does the work
  -----------------------------------  ----------------------------------------
  IO_PIN_ORDER_CFG = null (default)    OpenROAD.IOPlacement       (step 25)
  IO_PIN_ORDER_CFG = "<path>"          Odb.CustomIOPlacement      (step 26)
  FP_DEF_TEMPLATE  = "<path>"          Odb.ApplyDEFTemplate       (step 27)

Exact self-skip logic in v3.0.6:
  * OpenROAD.IOPlacement skips itself if IO_PIN_ORDER_CFG is not null,
    and also skips itself if FP_DEF_TEMPLATE is not null.
  * Odb.CustomIOPlacement skips itself if IO_PIN_ORDER_CFG is null,
    logging "No custom I/O placement file configured, skipping…".

# When default IO placement use the below

python3 -m librelane --dockerized ./config.json --last-run --from OpenROAD.IOPlacement --to OpenROAD.IOPlacement

# When custom IO placement use the below

python3 -m librelane --dockerized ./config.json --last-run --from Odb.CustomIOPlacement --to Odb.CustomIOPlacement

(Short forms, identical behaviour:)

    python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.IOPlacement
    python3 -m librelane --dockerized ./config.json --last-run --only Odb.CustomIOPlacement

To switch from default to custom, you must edit config.json - there is no CLI
flag for it. Either edit the file, or override for one run only:

    python3 -m librelane --dockerized ./config.json --run-tag "$TAG" \
        -c 'IO_PIN_ORDER_CFG="dir::pin_order.cfg"'

Note IO_PIN_ORDER_CFG replaces the OpenLane-era name FP_PIN_ORDER_CFG.
FP_PIN_ORDER_CFG is still accepted as a deprecated alias in config.json, but
it is NOT accepted by `-c`/--override-config, which requires current names.
Use IO_PIN_ORDER_CFG.

Pin order config file syntax (per the official reference):

    #N / #S / #E / #W       start the north / south / east / west section
    <regex>                 a pin name as a regular expression; regex
                            metacharacters must be escaped, e.g. x\[0\]
    @min_distance=<um>      minimum spacing between pins; global or per-section
    @bus_major              sort by bus name then bit number  (default)
    @bit_major              sort by bit number then bus name
    $<n>                    insert n virtual/placeholder pins

    Example:
        #N
        @min_distance=0.1
        x.*

        #S
        $1
        rst

        #E
        clk

        #W
        p
        y


--------------------------------------------------------------------------------
 7.2  MACRO PLACEMENT   (step 17 in Classic)
--------------------------------------------------------------------------------
Relevant config variables:  MACROS (current, preferred)
                            MACRO_PLACEMENT_CFG (accepted, but the step logs
                            "Using 'MACRO_PLACEMENT_CFG' is deprecated. It is
                            recommended to use the new 'MACROS' configuration
                            variable.")

Odb.ManualMacroPlacement is the ONE step for both cases - there is no separate
"auto" step ID. It skips itself when no macro instances are configured.

# When macro placement is automatic / there are no macros - nothing extra to
# run. The step self-skips.

# When macro locations are set manually (via MACROS, or the deprecated
# MACRO_PLACEMENT_CFG), use the below

python3 -m librelane --dockerized ./config.json --last-run --only Odb.ManualMacroPlacement

MACRO_PLACEMENT_CFG file format: line-break delimited, one instance per line,
    instance_name  X_pos  Y_pos  Orientation
Prefer MACROS instead for new designs.


--------------------------------------------------------------------------------
 7.3  STANDARD-CELL PLACEMENT OVERRIDE   (step 33 in Classic)
--------------------------------------------------------------------------------
Relevant config variable:  MANUAL_GLOBAL_PLACEMENTS

The step skips itself if MANUAL_GLOBAL_PLACEMENTS is null, logging
"'MANUAL_GLOBAL_PLACEMENTS' not set. Skipping…".

# When default placement - global placement decides everything; nothing extra
# to run, the step self-skips.

# When manual instance locations are configured, use the below

python3 -m librelane --dockerized ./config.json --last-run --only Odb.ManualGlobalPlacement

Per its own documentation, for a custom design with only a few cells this step
can be used in place of global placement entirely.


--------------------------------------------------------------------------------
 7.4  ANTENNA DIODE INSERTION   (steps 42-44)
--------------------------------------------------------------------------------
Three distinct strategies, all present in the Classic flow, each gated by
config:

# Unconditional diodes on every design port
python3 -m librelane --dockerized ./config.json --last-run --only Odb.DiodesOnPorts

# Heuristic insertion based on estimated net length
python3 -m librelane --dockerized ./config.json --last-run --only Odb.HeuristicDiodeInsertion

# OpenROAD's own repair pass, driven by real antenna violations
python3 -m librelane --dockerized ./config.json --last-run --only OpenROAD.RepairAntennas


--------------------------------------------------------------------------------
 7.5  OVERRIDING ANY CONFIG VARIABLE FOR ONE RUN
--------------------------------------------------------------------------------
-c / --override-config takes KEY=VALUE where VALUE must be valid JSON, and KEY
must be the current (non-deprecated) name. Repeatable.

    python3 -m librelane --dockerized ./config.json --run-tag "$TAG" \
        -c 'FP_CORE_UTIL=40' \
        -c 'PL_TARGET_DENSITY=0.6' \
        -c 'CLOCK_PERIOD=10'

Strings need JSON quoting, which means quoting the whole argument in bash:

        -c 'DESIGN_NAME="full_adder"'

================================================================================
 9.  RUNNING / RE-RUNNING A SINGLE STEP OUTSIDE A FLOW
================================================================================

The step-level CLI is a SEPARATE entry point:

    python3 -m librelane.steps --help

Three subcommands: run, eject, create-reproducible.

9.1  Re-run one step from its own saved config + state
     (each step directory under runs/$TAG/ contains both):

    python3 -m librelane.steps run \
        -c ./runs/$TAG/47-openroad-detailedrouting/config.json \
        -i ./runs/$TAG/46-openroad-stamidpnr-3/state_out.json \
        -o ./step_rerun

     --id is only needed if the config file lacks .meta.step.

9.2  Package a step as a filesystem-independent reproducible, for bug reports:

    python3 -m librelane.steps create-reproducible \
        -d ./runs/$TAG/47-openroad-detailedrouting \
        -o ./repro

     Or straight from a flow run, which builds the reproducible then aborts:

    python3 -m librelane --dockerized ./config.json --last-run \
        --reproducible OpenROAD.DetailedRouting

9.3  "Eject" a step into a plain shell script that calls the underlying tool
     directly - for reporting issues upstream to OpenROAD/Magic/KLayout:

    python3 -m librelane.steps eject \
        -c ./runs/$TAG/47-openroad-detailedrouting/config.json \
        -i ./runs/$TAG/46-openroad-stamidpnr-3/state_out.json \
        -o ./run.sh

 10.  OUTPUT DIRECTORY LAYOUT
================================================================================

    runs/$TAG/
        <NN>-<step-id-lowercased>/       one per executed step, NN = ordinal
            config.json                  the exact config that step saw
            state_out.json               the design state it produced
            reports/                     its reports
            *.log                        tool output
        final/                           consolidated deliverables
            gds/        def/    lef/     odb/    nl/     pnl/

            sdc/        lib/    json_h/  vh/     render/
            metrics.csv
            metrics.json
        error.log / warning.log / flow.log (when produced)

STEP DIRECTORY NUMBERS DO **NOT** ALWAYS MATCH SECTION 12 (v1 said they did)

The ordinal counter increments ONLY for steps that actually execute. Gated
steps (section 4A) consume no ordinal and create no directory. So:

    directory ordinal  =  section-12 number
                          MINUS the number of gated steps before it

With the four stock-default gated steps, a clean Classic run produces 76
directories numbered 01-76, not 80. Verified mapping from the mux8x1 run:

    Section 12 no.  Step                            Directory
    --------------  ------------------------------  ---------------------------
     1-40           Verilator.Lint … CheckAntennas   01-40   (identical)
     41             OpenROAD.RepairDesignPostGRT     (gated - NO DIRECTORY)
     42             Odb.DiodesOnPorts                41
     43             Odb.HeuristicDiodeInsertion      (gated - NO DIRECTORY)
     44             OpenROAD.RepairAntennas          42
     45             OpenROAD.ResizerTimingPostGRT    (gated - NO DIRECTORY)
     46             OpenROAD.STAMidPNR-3             43
     47             OpenROAD.DetailedRouting         44
     48-74          Odb.RemoveRoutingObstructions …  45-71   (offset -3)
                    Checker.LVS
     75             Yosys.EQY                        (gated - NO DIRECTORY)
     76-80          Checker.SetupViolations …        72-76   (offset -4)
                    Misc.ReportManufacturability

So in a stock run it is 06-yosys-synthesis and 21-openroad-generatepdn as v1
said, but 58-klayout-streamout, NOT 61-klayout-streamout.

NEVER hardcode these numbers in a script. Find the directory by name:

    ls -d runs/$TAG/*-klayout-streamout
    ls -d runs/$TAG/*-yosys-synthesis

Two further things that shift the numbering:
  * Re-running a range APPENDS new numbered directories; it does not overwrite
    the old ones. Running the same range twice gives you two copies.
  * Any invocation that restarts from step 1 (see section 4.2) duplicates the
    early steps and shifts everything after them.

Getting at the GDSII:

    ls runs/$TAG/final/gds/
    klayout runs/$TAG/final/gds/<DESIGN_NAME>.gds

If no --run-tag is given, $TAG is auto-generated as RUN_YYYY-MM-DD_HH-MM-SS
in local time.


================================================================================
 11.  RULES YOU MUST NOT BREAK
================================================================================

(1) ORDER IS NOT OPTIONAL, AND RUNNING OUT OF ORDER DOES NOT ERROR.

    --last-run picks the run directory with the newest modification time.
    Within that directory, if you do not pass -i, the initial state is the
    NEWEST state_out.json by modification time, found recursively - not the
    state that logically precedes your --from step.
    (librelane/flows/flow.py, librelane/common/misc.py: get_latest_file)

    Consequence: if you run I/O placement before PDN, LibreLane will not
    complain. It will feed the wrong state forward and you get a broken or
    silently degraded design. Follow section 12's numbering.

(2) --run-tag AND --last-run ARE MUTUALLY EXCLUSIVE.

    Passing both raises "tag and last_run cannot be used simultaneously."
    Pick one convention per session and keep to it.

(3) --dockerized MUST COME FIRST.  See section 1 for the exact rule.

(4) DO NOT SKIP THE REPAIR AND RESIZER STEPS THAT ARE ON BY DEFAULT.
    [CORRECTED IN v2 - v1 got this wrong.]

    ON BY DEFAULT - never exclude these from your ranges:
        OpenROAD.RepairDesignPostGPL   (32)  RUN_POST_GPL_DESIGN_REPAIR=True
        OpenROAD.ResizerTimingPostCTS  (37)  RUN_POST_CTS_RESIZER_TIMING=True
        OpenROAD.RepairAntennas        (44)  RUN_ANTENNA_REPAIR=True

    OFF BY DEFAULT - v1 wrongly listed these as must-not-skip. You cannot
    "not skip" them; they never run unless you explicitly enable them, and
    upstream calls them experimental (see section 4A.2):
        OpenROAD.RepairDesignPostGRT   (41)  RUN_POST_GRT_DESIGN_REPAIR=False
        OpenROAD.ResizerTimingPostGRT  (45)  RUN_POST_GRT_RESIZER_TIMING=False

    The underlying warning still stands: a step list that jumps straight from
    GlobalPlacement to DetailedPlacement to CTS to routing will complete and
    produce a GDSII with unfixed slew, fanout and antenna violations. Use the
    section 4 ranges rather than cherry-picking single steps.

(5) STEPS THAT APPEAR MORE THAN ONCE GET A NUMERIC SUFFIX.

    OpenROAD.STAMidPNR, -1, -2, -3 are four separate invocations at steps 31,
    36, 38, 46. OpenROAD.CheckAntennas and CheckAntennas-1 are steps 40 and
    49. You must use the exact suffixed ID to target a specific one.

(6) CHECKERS ARE NOT ANALYSES.

    Checker.* steps compute nothing. They read a report produced by an earlier
    step and decide whether to abort the flow. Checker.XOR without KLayout.XOR,
    or Checker.LVS without Netgen.LVS, has nothing to read.

(7) --from A --to B IS A RANGE, NOT A PAIR.

    "--from Magic.DRC --to Checker.KLayoutDRC" runs steps 67, 68, 69 AND 70.

(8) --only X IS THE SHORTHAND FOR --from X --to X, AND OVERRIDES BOTH.

(9) SELF-SKIPPING STEPS ARE NOT ERRORS.

    Several steps decide at runtime to do nothing (section 7). Read the log
    line - "skipping <id>…" - rather than assuming the step did the work.

(10) DEPRECATED CONFIG NAMES ARE ACCEPTED IN config.json, NOT IN -c.

     Examples of renames in this version:
         FP_PIN_ORDER_CFG          -> IO_PIN_ORDER_CFG
         GRT_OBS                   -> ROUTING_OBSTRUCTIONS
         QUIT_ON_UNMATCHED_IO      -> ERRORS_ON_UNMATCHED_IO
         MACRO_PLACEMENT_CFG       -> MACROS
     Prefer current names everywhere.

(11) --to WITHOUT --from ALWAYS STARTS AT STEP 1.  [NEW IN v2]

     `--run-tag "$TAG" --to X` on an EXISTING run re-runs everything from
     step 1 into that same run directory, duplicating the early steps. It does
     not resume. Use it exactly once, to create the run. Every stage after
     that must be `--last-run --from A --to B`. See section 4.2.

(12) --docker-no-tty IS FOR NON-INTERACTIVE SHELLS ONLY.  [NEW IN v2]

     Do NOT add it to commands you type by hand - the plain --dockerized form
     used throughout sections 4 and 5 is correct in any terminal, confirmed by
     the controlled test in section 1.

     Add it only where stdin is not a terminal (scripts, pipelines, cron, CI,
     ssh without -t, agent harnesses). There, without it, dockerized runs fail
     instantly with "cannot attach stdin to a TTY-enabled container".

(13) GATED STEPS ARE NOT THE SAME AS SELF-SKIPPING STEPS.  [NEW IN v2]

     See section 4A. Gated steps create no directory and consume no ordinal;
     self-skipping steps create a directory with no tool output. Four Classic
     steps are gated off by default.

================================================================================
 14.  TROUBLESHOOTING
================================================================================

Warnings seem to be missing while a run is in progress
    LibreLane collects step warnings and prints them ONCE, in a summary block
    at the very end ("The following warnings were generated by the flow:",
    librelane/flows/flow.py:699). Grepping a log mid-run will not find them
    and gives a false all-clear. Wait for the process to exit, or read
    runs/$TAG/warning.log instead.

"cannot attach stdin to a TTY-enabled container because stdin is not a terminal"
    Your shell has no TTY. Add --docker-no-tty BEFORE --dockerized. Section 1.

A step ran but produced no directory at all
    It is gated off by a RUN_* variable. Section 4A. Check with:
        grep "Gating variable" runs/$TAG/flow.log

Step directory numbers do not match section 12
    Expected - see section 10. Locate directories by name, not number:
        ls -d runs/$TAG/*-klayout-streamout

Lint (or synthesis) appears twice in the run directory
    You used `--run-tag "$TAG" --to X` on an existing run, which restarts from
    step 1. Section 4.2 and rule (11).

Flow fails at a checker
    The checker names the report it read. Open the corresponding step
    directory under runs/$TAG/ and read reports/ there. Fix the CAUSE, then
    re-run from the step that produced the report, not from the checker.

"Run directory already exists"
    Add --overwrite, or pick a new tag.

"tag and last_run cannot be used simultaneously"
    You passed both --run-tag and --last-run. Drop one.

"last_run used without any existing runs"
    You used --last-run before any run existed. Start with --run-tag.

Path starting with a tilde is rejected
    Let bash expand it: `--pdk-root ~/.ciel`, never `--pdk-root=~/.ciel` and
    never `--pdk-root "~/.ciel"`. Or use an absolute path.

Wrong design state after re-running an early step
    Once you re-run step 20, the states written by steps 21-80 are stale but
    still on disk. Initial-state selection is by modification time, so it
    usually resolves correctly - but the safe move after re-running an early
    step is to continue forward with an explicit range, or pin the state
    explicitly with -i.

Detailed routing takes forever or fails to converge
    Almost always a placement density or PDN problem, not a router problem.
    Lower PL_TARGET_DENSITY or FP_CORE_UTIL and re-run from floorplan.

GUI does not open under --dockerized
    xhost +local:docker
    and confirm $DISPLAY is set in the shell you launch from.

OpenROAD GUI warns "[GUI-0076] qglx_findConfig: Failed to finding matching
FBConfig for QSurfaceFormat…"
    Qt could not negotiate a matching GLX/OpenGL visual inside the container.
    Seen on hosts carrying only Mesa software GL with no vendor GPU driver
    (check with `ls /usr/lib/x86_64-linux-gnu/libGLX*`). KLayout does not emit
    it because it does not request a GL context the same way.

    MEASURED, NOT ASSUMED: setting LIBGL_ALWAYS_SOFTWARE=1 does NOT suppress
    this warning. Two runs of OpenInOpenROAD on the same design - one via
    --dockerized, one via a hand-written `docker run` with
    LIBGL_ALWAYS_SOFTWARE=1 - produced byte-identical output (1995 bytes),
    both containing exactly one GUI-0076 warning. Do not reach for that
    variable expecting it to help.

    In both runs OpenROAD still reached "Flow complete" and exited 0, which is
    consistent with the warning being non-fatal and Qt continuing anyway. If
    your window does appear, treat GUI-0076 as noise and ignore it.

    If the window genuinely does NOT appear, this warning is not enough to
    conclude GL is the cause. Isolate it first:
      1. Open the same run in KLayout (--flow OpenInKLayout). If KLayout shows
         and OpenROAD does not, the problem is OpenROAD/Qt/GL, not X11.
      2. If NEITHER shows, the problem is X11: re-run `xhost +local:docker`,
         confirm $DISPLAY is set, and confirm /tmp/.X11-unix exists.

    For reference, the equivalent hand-written container invocation (verified
    to run - `--version` and the full OpenInOpenROAD flow both succeed through
    it) is below. Use it when you need to set an env var that --dockerized
    will not forward; note --docker-mount CANNOT inject -e flags (section 1):

        docker run --rm -it \
            -e DISPLAY="$DISPLAY" \
            -v /tmp/.X11-unix:/tmp/.X11-unix \
            -v "$HOME:$HOME" -v "$HOME/.ciel:$HOME/.ciel" \
            -e PDK_ROOT="$HOME/.ciel" \
            -w "$PWD" --network host --security-opt seccomp=unconfined \
            --user "$(id -u):$(id -g)" \
            ghcr.io/librelane/librelane:3.0.6 \
            python3 -m librelane ./config.json --last-run --flow OpenInOpenROAD

    (No --dockerized inside the container - you are already in it.)

A step "did nothing"
    Check the log for "skipping <id>…". See section 7 - several steps
    self-skip based on config.

Inspect any step's inputs and outputs
    runs/$TAG/<NN>-<step-name>/
        config.json      the exact configuration that step saw
        state_out.json   the design state it produced
        reports/         its reports
        *.log            tool output

See what the step CLI accepts
    python3 -m librelane.steps --help
    python3 -m librelane.steps run --help
